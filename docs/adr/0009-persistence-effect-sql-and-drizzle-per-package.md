# 永続化は Effect SQL と Drizzle 1.0 RC で書き、スキーマとマイグレーションはパッケージが持つ

SQLite には `@effect/sql-sqlite-bun` の接続を `apps/host` に 1 本だけ開き、その上に Drizzle 1.0 RC の `drizzle-orm/effect-sqlite-bun` を載せる。ホストでは複数のターン、ツールの関所の先書き、送信、受信が同じプロセスの fiber として並行に書く。Effect SQL は接続を排他で囲い、トランザクションを終わりまで握るので、並行する書き込みが他のトランザクションに混ざらない（実測）。素の bun:sqlite と Drizzle 0.45 の bun-sqlite では、トランザクションに async の処理を渡すと最初の `await` で確定し、失敗しても書き込みが残った。手で `BEGIN` を書くと、並行した書き込みが混ざって巻き戻しで消えた（どちらも実測、型検査は通る）。Drizzle は TS のスキーマを 1 か所に置くことと、drizzle-kit によるマイグレーションの生成のために使い、RC であることは版の固定で受け入れる。

各ドメインのパッケージは、自分の表の定義、マイグレーション、記録用の表（`__drizzle_migrations_<パッケージ>`）を持ち、`apps/host` は起動時に各パッケージのマイグレーションを当てるだけにする。パッケージをまたぐ外部キーとトランザクションは使わず、他のパッケージの行は id で指す。そのため、マイグレーションを当てる順番がパッケージの間で問題にならない。

## Considered Options

- Effect SQL だけ: 依存は増えないが、DDL を手で書き、スキーマと型が別々になる。
- Drizzle 0.45 と bun:sqlite（Monica の形）: トランザクションを同期の関数に限る規律と lint に頼ることになる。
- bun:sqlite を直接使う: 排他とマイグレーションを自分で作り直すことになる。
- マイグレーションを `apps/host` に 1 本でまとめる: 動いたが、スキーマはドメインが持つのに履歴はアプリが持つ形になる。

## Consequences

- drizzle-orm と drizzle-kit は `1.0.0-rc.6` に固定する。上げるときは、並行トランザクション、外部キー、マイグレーションの確認を流し直す。SQLite 向けの Effect ドライバには公式の文書がなく、ソースが頼りになる。
- 記録用の表を共有すると、Drizzle は片方のパッケージのマイグレーションを黙って飛ばした（実測）。記録用の表はパッケージごとに分ける。
- トランザクションの中では SQL だけを流す。中で 200ms 待つトランザクションがあると、ツールの関所の書き込みの p99 が 0.4ms から 200ms になった（実測）。
- 外部キーは既定で効かない。マイグレーションは外部キーを切ったまま当て、そのあと `PRAGMA foreign_keys = ON` と `PRAGMA foreign_key_check` を流す。トランザクションの中では外部キーの PRAGMA が効かないので、drizzle-kit が書き出す `PRAGMA foreign_keys=OFF` は効かない（実測）。
- `synchronous=FULL` にする。ツールの関所の先書きの記録が、電源断で消えないようにするため。Mac では負荷のもとで p99 0.85ms だった。Linux での値は未測定。
- Drizzle の表の定義には STRICT がないので、列の値は CHECK で縛る。
